Case study, analytics tooling built with an AI agent

I connected an AI agent to a live analytics stack and used it to build the tools my team needed.

Over 32 days on the data team at a subscription streaming service, I worked with a coding agent that could read our transformation code, query the warehouse, and create content in our BI tool. This page shows what came out of that, and the working rules that made the output trustworthy.

Build 1

A lineage explorer that showed what was safe to delete

The team was planning a cleanup of the BI layer and needed to know, for every dashboard, which data it depended on and whether anyone still opened it. A colleague had already mapped one data domain. I built the second domain's map with the agent, as a single self-contained HTML file anyone could open in a browser.

The agent traced every dependency reference in the transformation code, opened each view definition in the BI project to confirm which table it read from, then queried the BI tool's usage logs to bind every dashboard tile and saved report to the explore it runs on. I had it pull 30-day usage straight into the file instead of handing me CSVs to merge.

The first version guessed the dashboard wiring from dashboard titles. I asked which parts were inferred and had every one of them verified against the logs. That pass corrected seven mappings, added nine dashboards the guess had missed, and removed five that did not belong. I also caught that its usage metric counted tile queries, where the existing map counted dashboard loads, and had it matched so the two maps could be read side by side.

Reconstruction, invented names and numbers
Hot, 30 or more loads in 30 days Active, 1 to 29 Cold, 0

Click any node to trace everything upstream and downstream of it. Filter to Cold and the cleanup list writes itself. The original covered dozens of dashboards and well over a hundred saved reports, and it showed that more than half of those dashboards and roughly nine in ten of the saved reports had gone unused for a month.

What it saved: the alternative was opening each dashboard and saved report one at a time to see what it queried. The team used the maps as the basis for the cleanup, and I drafted a phased cleanup outline from the two of them.

Builds 2 to 4

Three more, same method

Tracing a customer count that would not reconcile

Problem
A query for active customers came in well under the reference figure, and I was asked to find out where the missing group went.
What the agent did
Annotated the SQL line by line, ran it against the warehouse, and tested the cohort logic against the underlying models.
Outcome
The gap was a filter that anchored on free-trial starts, which silently dropped customers who began on a paid plan and customers who returned. I delivered a corrected query, then adjusted it again to match the stakeholder's own formula exactly.

A refresh timeline generated from the pipeline's own config

Problem
The team needed a clear picture of when each day's data actually lands, across several scheduled jobs.
What the agent did
Read the ingestion schedule, the scheduled transformation runs and the freshness thresholds from the repository, then wrote a Python script that renders them as one timeline across three data domains.
Outcome
A chart in the team's time zone, with the generator script saved next to it so it can be re-run when schedules change. The follow-up was a proposal for a daily completeness check that posts to Slack.

A stakeholder dashboard built through the BI tool's API

Problem
A stakeholder asked for a content ranking view built on a new definition of early viewing.
What the agent did
Copied the existing dashboard into my folder, built replacement tiles and filters through the BI connection, and ran a QA pass on the numbers before handoff.
Outcome
A first version on the fields that already existed, then a rebuild on the new model the data engineering team shipped, with an explainer tile so readers know what they are looking at.

The same setup also produced the planning work for the larger goal: rebuilding the warehouse so that a conversational agent could answer business questions accurately. I reviewed the rebuild's planning documents for what an agent would need, and my pull requests added a business glossary and a metric registry to the requirements, so that definitions live in machine-readable form beside the code. The project plan I drafted includes a test bench of stakeholder questions with known correct answers, to catch documentation gaps before anyone relies on the agent.

Working rules

What made the agent's output usable

An agent with access produces plausible work fast, and plausible is the risk. Claude Code's own usage report for the month counted 13 times I redirected a wrong approach. These are the rules that came out of those corrections.

7dashboard mappings wrong before the verification pass
13wrong approaches caught and redirected
9dashboards the first pass had missed entirely
  1. 01

    Make it say what it inferred

    Every artifact gets the question: which parts did you verify and which did you guess? On the lineage map, the guessed parts were the ones that were wrong.

  2. 02

    Read the whole source first

    On a forecasting spec, the agent critiqued the document after reading one tab of two multi-tab workbooks. I stopped it and had it reread everything before either of us drew conclusions.

  3. 03

    Use the stakeholder's formula, not a reasonable substitute

    Twice the agent chose a metric that was defensible and different from the one the business already used. Matching the existing definition is what makes a number comparable.

  4. 04

    Ask whether it is a permissions problem before adding a tool

    When a metadata pull failed, the suggestion was to install a second connector described as official. I asked for confirmation, and it turned out to be a third-party package. The likelier cause was access scope on the connector we already had.

  5. 05

    Write the lesson where the agent will load it

    After one difficult request I wrote up what went wrong on both sides and had it saved to persistent memory, so later sessions started with those rules already loaded.
